## 2. R1：停留证据窗口更正

### 2.1 修正方法

对每条停留候选，从 `evidence_frame_video_time`（触发帧）向前回溯，按目标 `track_id` 的实际 `inside/dwell` 观测计数 50 个有效样本（5 FPS × 0.2 秒 = 10.0 秒），直到首个 `dwell=0.2` 样本。缺帧只会增大墙钟跨度，不增加有效观测秒数。

- **因果窗口**：真实观测起点 → 触发帧；用于证据和复核。
- **条件时刻**：触发帧后的下一采样步，单独保存为 post-trigger context，**不计入 10 秒依据**。
- **有效观测**：50 个样本 × 0.2 秒 = 10.00 秒。
- **观测跨度至条件**：真实起点 → 条件时刻；缺帧 + 下一采样步共同形成跨度。
- **登记窗口**：首次写入 ledger 的 `evidence_start/evidence_end`，为保持 `candidate_key` 和 18 个旧映射不变而保留；新增字段明确其只作身份保留。

## 3. R2：时钟边界与精度口径

### 3.1 首帧/覆盖终点语义

Frigate 录像数据库区间是 `[start_time, end_time]`，`end_time = start_time + duration`，其中 `end_time` 是**覆盖终点**，不是末帧 PTS。25 FPS 下末帧 PTS 比覆盖终点早 0.04 秒。

- 旧：`t0 = end_time - last_frame_pts` → `1793805307.04`（晚 40 ms）。
- 新：同时使用
  - `t0_from_start = start_time - first_frame_pts`
  - `t0_from_last_coverage_end = end_time - (last_frame_pts + 0.04)`
- 14 段两端差均为 `0.00`；最终 `t0=1793805307.0`，`boundary_correction=-0.0400s`。
- 最终拟合使用 **14 段 × 2 端点 = 28 个锚点**；`drift≈0`，数值残差 0.000 秒。
- 容器 PTS 非零起点不由容器 PTS 当绝对时钟：录像段用首帧烧录帧号锚定源时刻；下载 clip 的 `start: 0.08` 只作相对播放偏移，clip 内对齐以首帧烧录帧号为锚点。

## 4. R3：服务端复核准入与播放器补验

### 4.1 服务端准入

`demo/serve.py` 在写入 `Ledger.add_review` 前调用 `src/st_memory/unified_review_guard.py`，独立校验：

1. `clock.status == verified`；
2. `replay_id`、`camera`、`loop_index`、`source_video_sha256` 与当前回放/源一致；
3. `evidence.status == verified` 且 `evidence.window.condition_ok == True`；
4. `clip.http_status == 200`、`clip.decoded == True`、`clip.coverage.status == verified`；
5. `event_id` 与 ledger 行一致、`ledger_key` 一致；
6. `rule_window_start < rule_window_end`；
7. 证据文件存在，且 SHA256 与 `clip.sha256` 一致。

任一失败返回 **409**，不写入 review；旧三例没有新 clock/evidence 字段，走 `validate_legacy_review`（key + 文件存在），不破坏历史复核页。
